## 1. 目标和成功条件

本阶段要解决四类问题：

1. **文件职责不清和规则重复**：每个重要文件、目录都有明确目的、权威等级、生命周期、依赖与允许的发行范围；规则只有一个正式定义。
2. **核心规划文档失焦**：当前实施状态与历史记录分离；Agent 首先看到可执行的当前指针，而不是必须解析大量过期叙述。
3. **旧项目接入侵入性过大**：AgentOrch 自有文件集中在下游项目根目录的 `agentorch/`；宿主项目既有结构不被打散，根 `AGENTS.md` 只接受有边界、可幂等更新的扩展。
4. **模型选择缺少资源效率和评价可信度**：基于真实 Token 用量、经验证的有效工作贡献与互相独立的评价证据，改善 Execution / Reviewer 的选择；Master 保持用户手动选型。

成功不以“多了多少文档 / 指标”判定，而以是否可验证地减少路径歧义、文档漂移、错误选型、无效 Token 消耗和下游安装损坏判定。

## 2. 权威文件与责任边界

### 2.1 既有权威关系保持不变

| 位置 | 唯一职责 |
|---|---|
| `README.md` | 项目简介、核心能力、快速入口、基本安装路径 |
| `docs/README.md` | 完整用户手册、安装 / 升级 / 故障处理与文档导航 |
| `docs/PLAN.md` | 设计目标、原则、范围与非目标 |
| `docs/implementation-plan.md` | 当前阶段、任务依赖、未完成工作、阻塞与近期推进顺序 |
| `docs/PROJECT.md` | 当前项目适配配置、edition、路径和验证命令 |
| `AGENTS.md` | Agent 协作、权限、操作纪律与项目推进入口 |
| `docs/orchestration.md`（迁移目标） | 核心编排契约、状态机、证据门禁与关键流程 |
| `editions/<edition>/` | local / github 底座的操作手册 |
| `docs/design/` | 已审查的设计契约与架构方案；明确状态并链接实施 Issue |
| `scripts/`、`tests/` | 实现与可重复验证 |
| `release/`、发行清单 | 发行构建、发布说明、包内文件边界 |

上述权威关系只声明职责，不应把字段、状态、门禁或能力定义复制到多个文件。变更权威定义时，必须同步影响分析和对应验证，而非在引用文档中平行建立第二套规则。

### 2.2 文件用途分类与生命周期

文件用途分类至少为：

- `authoritative`：某项规则、数据结构或契约的唯一正式定义。
- `reference`：导航、用户说明或对权威规则的引用；不重复定义规则。
- `implementation`：源码、测试、验证器、构建及迁移逻辑。
- `derived-local`：生成文件、机器私有记录或本机配置；必须明确是否入库、同步、打包。
- `outdated`：已过时、被替代或仅供历史追溯的文件；默认不进入 Agent 的当前阅读路径。

用途类别与生命周期状态是两个独立维度。文件可以是过时的 reference，也可以是已完成但仍有效的 authoritative 文档。生命周期状态建议包括：

| 状态 | 意义与要求 |
|---|---|
| `PROPOSED` | 提议中；不能作为已冻结规范驱动实现 |
| `ACTIVE` | 当前有效，允许按正式任务维护 |
| `IMPLEMENTED` | 对应一次性计划已完成并有验收证据；若仍是现行权威规则，不能因此归档 |
| `DROPPED` | 已决定不实施；必须写明原因和决定依据 |
| `SUPERSEDED` | 被新文件 / 新决策取代；明确替代链接并移出当前阅读路径 |
| `ARCHIVED` | 仅为历史、审计或兼容性追溯保留 |

`outdated` 不是无限期囤积的许可：每个过时文件都必须指定替代文件或决定、归档理由、是否仍有审计 / 兼容价值，以及最终保留或删除决定。若无追溯价值且依赖已消失，应删除而不是永久归档。

拟新增：
- `docs/architecture/repository-map.md`：目录地图、关键文件责任、权威来源、引用关系、是否进入发行包、当前状态和首要阅读入口。
- `docs/architecture/document-lifecycle.md`：新增、更新、弃用、迁移、归档 / 删除和过时文件退出流程。

无需为每一个源码文件制造独立说明文档。中央地图负责关键责任；只有特殊约束无法从目录 / 自动检查表达时，才在单文件顶部登记例外。

### 2.3 文档影响记录

凡影响项目目标、规则、行为、接口、文件布局、运行方式、发行内容或迁移的任务，都必须提供文档影响记录。对每份受检文档使用：

- `UPDATE`：必须修改，提交中应有实际对应变更。
- `NO_CHANGE`：已检查，现有内容仍正确，说明依据。
- `NOT_APPLICABLE`：与本次变更无关，说明理由。

不能用“文档已同步”这类笼统陈述替代逐项记录。测试 / 结构重构若完全不改变用户行为，也要明确说明受影响的用户文档为何可保持不变。

## 3. 核心编排契约迁移

### 3.1 目标路径

当前 `kit/` 只有 `kit/orchestration.md` 一份文件，因此计划将其迁移为 `docs/orchestration.md`，不为孤立文件建立 `docs/kit/`。未来如出现多个职责一致的 kit 类契约，再依据文件地图统一规划子目录。

### 3.2 兼容 / 迁移要求

迁移前先审查以下所有路径假设：

- `AGENTS.md`、两个 edition 的 Master / Execution 手册、模板及所有文档链接。
- `scripts/validate_kit.py` 中的 `REQUIRED` 与文档验证逻辑。
- `scripts/build_release.py` 的发行文件收集、禁止路径和 package self-check。
- `update_agentorch` 的旧版本基线识别、文件分类、旧路径迁移及冲突报告。
- 发行包中的文件定位、相对链接、初始化 / 诊断入口和已有安装结构。
- 测试夹具、合成交付场景、文档导航与 README。

必须注意：上游仓库的 `docs/` 目前同时包含仅仓库专有文档，而部分打包逻辑对 `docs/` 有特殊处理。新的核心契约进入 `docs/` 后，必须依据文件映射显式区分“可以随发行包分发的核心契约”和“只属于上游开发仓库的设计 / 历史文档”，不能简单移除全部 `docs/` 禁止规则，也不能将所有文档打入发行包。

旧版本的 `kit/orchestration.md` 若有本地修改、目标路径已存在且内容不同、旧 manifest 缺失或升级基线不可靠，更新引擎必须停止并给出逐文件处理建议。不得直接覆盖、丢弃或伪称自动迁移成功。回滚方案应保留迁移前文件与 manifest 证据。

## 4. 核心计划清理和生命周期机制

### 4.1 `docs/implementation-plan.md` 的职责

该文件只承担当前推进指针：

- 当前阶段与最近一次状态快照。
- 未完成的任务、依赖、阻塞、下一步动作及所需决策。
- 当前阶段的出口条件以及引用证据。
- 对相关设计文档、Issue、PR、回归场景和发布记录的链接。

已完成任务的历史细节优先追溯原 Issue / PR / 发布记录。只有无法通过权威载体恢复、但仍有价值的决策或审计信息才需要归档。禁止在核心计划重复复制长篇已完成 Issue 描述、所有旧版本的全文摘要或已经过期的“当前状态”。

清理不能损失重要事实。迁移前应盘点每段内容的权威来源、状态准确性及追溯价值；随后将需要保留的历史转为链接或独立归档，并保留一份精简的迁移审计结果。不得凭模型推断关闭旧任务，也不得仅因为历史叙述较长就删除尚未解决的风险。

### 4.2 规划文档的退出条件

每份大型规划文档必须声明状态、负责人角色、所属 Epic / Issues、定义范围、当前未完成项和归档条件。

- `PROPOSED`：等待设计评审，不能作为实现的已冻结依据。
- `ACTIVE`：有明确的未完成交付或有效维护职责。
- `IMPLEMENTED`：全部必要验收已由证据验证；更新索引与当前计划。
- `DROPPED`：确认舍弃，记录理由和替代方案。
- `SUPERSEDED`：标明替代文件，移除当前入口。
- `ARCHIVED`：从默认用户 / Agent 阅读路径移走，但保留可追溯地址。

规划文档不能仅靠顶部状态手动自证完成。状态更新必须由对应 Issue / PR / 验证结果支撑。实现完成的长期规范可以继续保留为 ACTIVE authoritative 文档。

## 5. 文档与文件结构自动验证

首版将确定性检查纳入现有 `validate_kit.py`、单元测试、`build_release.py` 与 CI，不增加新的第三方运行时依赖。至少覆盖：

1. 重要文件路径、用途类别、生命周期和权威来源是否在 repository map 中登记或遵循明确的默认规则。
2. 所有当前入口、Markdown 相对链接和路径引用是否有效；旧的权威路径不得继续作为当前指令，兼容代码允许显式列入迁移登记。
3. 规则的权威文件与引用位置是否明确，避免多个入口复制冲突的定义；首版可从特定契约的链接 / 引用元数据开始，语义重复检测后续再增强。
4. 任务的文档影响记录是否完整，`UPDATE` 是否有对应变更，`NO_CHANGE` 与 `NOT_APPLICABLE` 是否提供理由。
5. 阶段计划中的活动任务和实际 Issue / PR / 验证事实是否有可追溯的一致来源；任何无法自动判断的情况报告给 Master，不得静默修改。
6. 源仓库必需文件、发行清单、包内自检和禁止分发路径一致。
7. AgentOrch 私有记录不提交、不上传、不进入发行包。

语义级漂移扫描只能作为诊断建议，不能自动覆盖文档或将猜测当作确定性错误。所有自动修复必须有明确的路径范围、差异报告和回滚方案。

## 6. 旧项目接入：`agentorch/` 隔离布局

### 6.1 目标布局

对于已有自己的文件结构、源码、配置和开发规则的项目，接入 AgentOrch 后采用下列结构（示意，具体发行文件以 manifest 为准）：

```text
host-project/
├── AGENTS.md                   # 保留原文，仅追加 / 更新受控的 AgentOrch 区段
├── <host-existing-files...>    # 原项目文件 / 目录保持原位、不重命名、不迁移
└── agentorch/                  # AgentOrch 自有发行内容的边界
    ├── README.md
    ├── docs/
    ├── editions/
    ├── scripts/
    ├── templates/
    ├── tests/                  # 仅当发行策略要求分发这些测试时
    ├── .gitignore              # 只忽略 agentorch/ 内部的运行时 / 私有数据
    └── .local/                 # 本机状态 / scope 记录，默认不入库、不打包
```

上图只表示边界与相对位置；最终哪些源码 / 测试在 Release 中分发，以唯一 manifest 为准。AgentOrch 根级的 `AGENTS.md` **不复制到 `agentorch/AGENTS.md`**。

### 6.2 宿主项目变更约束

安装 / 接入旧项目时，除新建 `agentorch/` 目录以及扩展宿主项目根 `AGENTS.md` 外，不得修改宿主项目其他文件或目录：

- 必须保留根 `AGENTS.md` 中已有内容；AgentOrch 作为一段具有明确 BEGIN / END 标记的增量区块追加。
- 更新必须幂等：重复运行不重复追加、不改变既有区块以外的宿主文字。
- 升级只替换由 AgentOrch 标记管理的区块；区块标记缺失、重复、不成对或用户对管理区块做了无法安全判断的修改时，停止并报告，不得覆盖。
- 不把宿主项目自身的 `AGENTS.md` 规则替换成通用套件文字。冲突按明确优先级处理，并通过新增区块说明 AgentOrch 如何作为项目推进引擎接入现有规则。
- 若根 `AGENTS.md` 不存在，则只新建这一份宿主入口文件；内容必须区分宿主项目规则和 AgentOrch 管理段，并报告这是创建而不是扩展已有内容。
- 若现有 `agentorch/` 已存在、非空或包含用户数据，必须先检测并输出冲突清单；默认不能覆盖。

### 6.3 相对路径和运行根

定义两个明确根目录：

- **Host Root**：宿主项目根目录，包含宿主的 `AGENTS.md` 和原项目文件。
- **AgentOrch Root**：`Host Root/agentorch/`，用于定位 AgentOrch 的脚本、模板、发行清单与内部文档。

必须让 `scripts/` 的项目根检测稳定地定位 AgentOrch Root，而不是把调用者当前工作目录当作根目录。AgentOrch 自身内部的文档链接相对于 AgentOrch Root 解析；需要引用宿主根 `AGENTS.md` 时，从所在文件计算正确的相对路径（例如从 `agentorch/docs/` 目录引用应回到两级父目录），并由测试真实解析路径，而不只是字符串替换。

工具必须显式区分：
- AgentOrch 内部路径（相对于 AgentOrch Root）；
- 宿主项目路径（相对于 Host Root，只有授权的根 `AGENTS.md` 扩展路径）；
- AgentOrch 私有数据路径（放在 `agentorch/.local/` 下，确保隔离且不入库 / 不打包）。

不能通过修改宿主项目根 `.gitignore` 来实现隔离。应在新增的 `agentorch/.gitignore` 或其他完全位于 `agentorch/` 内的机制中忽略本机数据、Worktree、缓存及私有记录；验证时确认根仓库规则和发行包不泄露这些内容。

### 6.4 安装 / 更新 / 回滚的验证

需要用合成宿主项目验证：

- 初始 `AGENTS.md` 可完整保留，追加区块后其原有内容作为前缀逐字节一致（仅允许规范化的尾部换行规则在设计中明确）。
- 重复安装 / 更新幂等。
- 更新只改动 `agentorch/` 内 AgentOrch 自有文件及 root `AGENTS.md` 的受控区块；其他 Host Root 文件的路径、内容和目录结构均不变。
- 相对链接、脚本发现、配置、scope、任务数据及更新引擎在从宿主根或任意工作目录调用时均按指定根目录运行。
- `agentorch/.local/`、本地任务状态、私有日志和 Worktree 不入 Git / 不入发行包。
- 目标冲突、旧 manifest 缺失、标记不完整、权限不足、旧版本迁移不安全时失败关闭。
- 回滚只回退 AgentOrch 管理的内容，不回退宿主项目其余文件，也不删除宿主已有的内容。

此布局是对发行 / 更新契约的变更，不能只在用户手册中写出新路径而不改动实际构建与更新机制。

## 7. 有效 Token 比率（ETR）

### 7.1 目标和限制

ETR 是“在有真实 Token 用量、且已完成评价的调用中，与有效工作贡献关联的 Token 当量占比”。它是工程代理指标，而不是对每个 Token 的语义价值作精确测量。

每次可评价调用应尽量记录：
- 精确底层模型 ID / 版本、Runtime / Agent alias、角色、任务类别和时间窗口；
- 供应商 / Runtime 报告的实际 input / output / cached / reasoning Token 字段及计量单位（按来源口径归一化，避免子字段重复计入总量）；
- 本次调用对应的任务、产出和可定位的验证 / 审查证据；
- 评价权重、评价状态、评价者身份 / 独立性和评价理由；
- Token 统计是否完整、来源是否真实、结果是否完成评价。

初始有效贡献权重建议：

| 结果 | 权重 | 要求 |
|---|---:|---|
| `EFFECTIVE` | 1.0 | 贡献经任务结果或独立证据验证，对目标推进有明确价值 |
| `PARTIAL` | 0.5 | 只有部分贡献可验证，或经过显著修改后才可用 |
| `INEFFECTIVE` | 0.0 | 有证据显示没有有效贡献、产生误导性结果或重复消耗但没有推进 |
| `UNRATED` | 不计入已评分分子 / 分母 | 评价尚未完成，不代表无效或有效；必须单独计算覆盖率 |

### 7.2 初始公式与覆盖率

对于已评分调用，令 (T_i) 为该调用已观测的 Token 总量，(w_i) 为有效贡献权重：

[
ETR = 100\% \times \frac{\sum_i T_i w_i}{\sum_i T_i}
]

ETR 分母仅包含被评价调用的已观测 Token；未评价 Token 不能自动当作无效或有效。还必须报告：

[
Token\ Coverage = 100\% \times \frac{\text{已评分调用的已观测 Token}}{\text{全部已观测 Token}}
]

ETR 只有在 Token 用量可观测、评价证据足够且覆盖率达到策略门槛时才可用于阈值决策。低覆盖率时可以报告“当前样本的 ETR”，但整体状态必须为 `UNKNOWN` / `PROVISIONAL`，不能触发自动淘汰或优先规则。

主指标可以使用总 Token 消耗衡量实际成本；为解释模型差异，报告还应尽可能展示 input / output / cached / reasoning 分项和上下文大小。输入 Token 往往受上游 Prompt、上下文长度及工具链影响，因此比较模型时应按角色 / 任务类型分组，记录 Runtime 与配置变化，避免将不同上下文工作负担简单误认为模型能力差异。

### 7.3 初始阈值策略

- 初始分数：50%，只作为 `PROVISIONAL` 中性先验，不可伪装为实测 50%。
- 初始低线：40%；初始高线：80%。二者是待真实使用数据校准的政策值。
- 建议暂定统计窗口为最近 90 天；达到至少 20 个已完成且可评价的任务，并且 Token 计量 / 评价覆盖率至少 80% 后，才能执行阈值动作。这是待验证的初始运营门槛，不是已经得到统计证明的通用结论。
- 低于 40% 且满足门槛：暂停该 `model ID × role × task category` 的**自动**选用；不删除候选、不永久禁止人工使用。记录排除原因并定义重新评测路径。
- 高于 80% 且满足门槛：在本任务所有硬约束、质量要求和评价可信度合格的候选中提高优先级；不能仅凭 ETR 证明正确性。
- 样本不足、Token 数据未知、模型 ID / Runtime / 配置变化或覆盖率不足：不得将缺失数据填成 0 或 100；报告 `UNKNOWN` / `PROVISIONAL` / `STALE` 并安全降级。
- 分数始终分开维护在模型身份、角色和任务类别之下；不得把 Execution 表现直接迁移为 Reviewer 评分。

## 8. 三角色互评与评价可信度

### 8.1 评价事件

Master、Execution、Reviewer 在实际参与且拥有可观察证据时可以互相评分。每个事件至少记录：评价者身份与模型 ID、被评价者身份与模型 ID、角色、任务 ID / 类别、评分维度、`+1 / 0 / -1` 或 `NOT_RATED`、证据引用、理由、时间戳、Runtime / 配置身份与评价者独立性。

`0` 是明确给出的中性评价（例如 Just Average）；`NOT_RATED` / `UNKNOWN` 是没有足够依据，不能折算为 0。不可只记录最终平均分而丢弃原始事件。

建议的关系与评价重点：

- Execution → Master：Prompt / task packet 的明确程度、验收可执行性、依赖 / 权限信息、是否因规划遗漏导致阻塞或返工。
- Reviewer → Execution：确认缺陷、严重程度、修复质量、遗漏风险、测试和证据完整性。
- Execution → Reviewer：审查意见可复现性、误报情况、具体性和修复建议可执行性。
- Master → Execution：目标符合度、范围纪律、首次验收、返工和合并后确认的回归缺陷。
- Master → Reviewer：真实问题发现、误报、漏报对照、风险覆盖与证据质量。
- Reviewer → Master：需求矛盾、验收遗漏、依赖遗漏、拆分不合理与设计风险。

评价维度需保持角色相关；不得把审查发现数量、Prompt 长度、工作量或 Token 消耗本身当作质量高低。

### 8.2 可信度状态与双评

建议评价可信度状态：
- `LOW`：只有单一评价者，或证据薄弱 / 不完整。
- `CORROBORATED`：至少两个经身份验证且独立的评价者，在查看彼此结论前，基于同一任务版本和同一证据范围独立作出一致评价，并有可定位依据。
- `CONFLICTED`：评价存在实质性冲突；需进一步独立核验或人工裁决。
- `UNKNOWN`：无法确认模型身份、评价材料、版本或独立性。

规则：
- 同一底层模型的不同名称、Alias、温度或提示词不能算独立评价者；不同模型家族优先，但家族未知时必须标记。
- 两条一致评价能提升可信度，但**同一事实只对质量分计一次**；不能因为双评而把一项事实重复加分。
- 评价必须尽量盲评，避免先看到对方分数后形成从众。
- 对 Reviewer 的漏报率，只有具备独立缺陷清单、合成缺陷测试或后续确认的真实缺陷对照时才可计算；没有对照时标记不可计算。
- 评价者本身的可信度需通过后来经独立证据确认的评价准确性校准。模型自信度、流畅表达和自我评价不能作为可靠性依据。
- 涉及 Master 自身的争议，Master 不能单方把争议判断为已解决；应使用另一个独立评价或可复现事实，必要时交用户裁决。

### 8.3 ETR 与互评如何结合

ETR 权重应由经核验的有效贡献评价产生，而不是由模型自评。双评可信度影响这项权重被采纳的确定性：

- 有直接、客观的任务验证证据时，可先按固定政策标为 EFFECTIVE / PARTIAL / INEFFECTIVE，并保留证据。
- 只有单一 Agent 主观判断且缺少独立验证时，结果应保持低可信 / 待复核，不能直接驱动淘汰或重用。
- 两个独立评价一致且与任务证据相符时，评价状态可升级为 `CORROBORATED`。
- 有冲突时保持 `CONFLICTED`，优先使用确定性验证、独立复核或人工决定，而不是简单平均成中性值。
- 评分与可信度是两个字段；不得把“评价者可信度”乘以 ETR 后，隐去原始值或制造看似精确但不可解释的总分。任何未来加权算法必须另有可测试的决策依据。

## 9. 多 Subagent 候选与选择边界

### 9.1 配置来源和身份

Execution / Reviewer 的候选来自用户在当前工具 / Runtime 中已经配置的 Subagent。类似 `builder-dsf`、`builder-glm`、`reviewer-grok`、`reviewer-gpt` 只是用户选择的候选名示例，不是写死在 AgentOrch 核心里的模型清单。

候选发现后必须映射并记录：
- 实际可调用的 Runtime / Agent alias；
- 精确底层模型 ID / 版本（无法确认则 UNKNOWN）及模型家族（无法确认也标 UNKNOWN）；
- 当前 Runtime 版本、工具 / 模态能力、权限、上下文和预算约束；
- 适用角色与能力证据、新鲜度；
- 该角色 / 任务类别下的 ETR、Token coverage、任务样本量、双评可信度、质量和成本数据。

复用 Phase D 的 Scope、本机 Markdown store、发现适配器、模型数据源与角色匹配，不另建一套本地数据库或角色状态机。

### 9.2 选择顺序

1. 确认真实调用路径、底层模型身份、当前 Runtime、Scope 与证据新鲜度。
2. 先做硬筛选：可调用性、所需模态、上下文、工具、授权、预算与 Reviewer / Execution 底层模型独立性。
3. 依据任务类型比较独立验证的正确性 / 交付质量、角色专项基准、具有足够覆盖率和可信度的 ETR、本地项目表现、成本与延迟。
4. 在具备足够样本和可信度时，应用 40% / 80% 的临时阈值规则。
5. 记录首选、备选、淘汰原因、身份 / 数据来源、可信度、覆盖率、未验证限制及是否需要人工决定。

不得让 ETR、总分、低成本或外部排行榜冲抵硬性限制。没有候选满足要求时停止自动选型，提供人工路径，而不是自动创建 / 授权新的 Subagent。

### 9.3 Master 由用户手动切换

Master 因具有产品目标理解、整体计划、冲突裁决和最终交付判断等特殊责任，始终由用户手动选择 / 切换。AgentOrch 可以提供 Master 当前模型的 ETR、历史表现、候选能力与替换建议，但不得自动修改 Master 的模型别名、系统 Prompt、工具配置或活动实例。

自动化的候选选择仅作用于预先配置且实际可调用的 Execution / Reviewer。没有真实运行时切换能力时，只输出可执行的推荐和人工操作步骤，不伪称已经切换。

### 9.4 防止模型垄断和恢复

低 ETR 模型在满足统计门槛后暂停自动选用，但保留手动评估 / 恢复路径。高 ETR 模型只是优先候选，不得垄断所有样本。对新模型、任务分布明显变化、模型 / Runtime 版本变化或数据过期的情况，应提供受控评估机会并重置 / 降级不再适用的历史可信度。

- `README.md`：产品级能力、基本使用方式和旧项目隔离安装方式发生变化时更新。

- `docs/PLAN.md`：仅当项目长期目标、原则、范围发生变化时更新；普通实施进度不改这里。
- `docs/implementation-plan.md`：阶段登记和状态唯一落点；只保留当前推进所需的信息。
- `docs/PROJECT.md`：只有 AgentOrch 上游仓库自身的适配配置 / 根路径语义有变化时更新，不将下游项目特例写入上游配置。
- `AGENTS.md`：协作契约或入口路径变化时更新；旧项目接入的合并区块规则必须是增量、幂等、可检测冲突，不得覆盖宿主规则。

- `repository-map.md` 与 `document-lifecycle.md`：文件职责、路径与生命周期规则的权威定义位置。

每个任务必须报告变更文档和未变更文档的理由，避免 README、用户手册、设计稿和阶段计划中出现互相矛盾的功能状态。

## 12. 风险和需要保留的限制

- **Token 观测差异**：不同 Runtime / 供应商未必暴露完全一致的 Token 细分；无法可信采集时 ETR 必须 UNKNOWN，不能用字符估算假装真实遥测。
- **归因限制**：一次调用可能同时产生有效和无效内容；调用级 0.5 是简化代理值，后续可依据可追溯证据细化，但不能没有证据就做 Token 级语义切分。
- **评价者相关性**：不同模型家族不保证独立，双评一致不替代确定性测试 / 事实证据。
- **模型版本变化**：底层模型 ID、Runtime、工具链或主要配置变化时，旧历史必须标明适用范围；不可未经核验直接迁移新版本成绩。
- **旧项目兼容**：`agentorch/` 内嵌目录会影响安装器、发行构建、路径定位及升级算法，必须做真实合成迁移 / 更新 / 回滚演练。
- **根 AGENTS 冲突**：用户改动受管理区块、标记不完整或原文无法安全保留时，应停止并交由用户决策。
- **历史清理**：不得以文档简洁为由丢失活跃风险、关键设计决策或无法从 GitHub 任务载体恢复的必要事实。
- **自动化边界**：不自动更改 Master、不扩大权限、不创建未授权 Subagent、不直接改写宿主项目目录、不自动删除宿主文件。
