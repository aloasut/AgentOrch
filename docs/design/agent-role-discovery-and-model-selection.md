# Agent 角色发现、Subagent 能力考核与动态模型选择设计

> 状态：设计提案，等待 Issue #117 对应 PR 审查与合并后冻结。
> 设计范围：通用 AgentOrch；不绑定特定 Agent Runtime、模型供应商、IDE 或单一项目。
> 本文定义目标架构和后续实施顺序，不宣称任何尚未接入的运行时接口、模型数据源或自动派发路径已经可用。

## 1. 目标与非目标

### 1.1 目标

AgentOrch 应在每次新会话或任务调度前，尽可能基于真实证据回答以下问题：

1. 当前 Master 所在的运行时是否能真实启动、隔离、等待并取回子代理结果？
2. 当前环境有哪些可用的 Agent / 子代理，分别具备什么已核验能力和权限边界？
3. 哪个候选适合担任本次任务的 Execution Agent 和 Reviewer Agent？
4. 可调用的模型中，哪些满足角色硬性条件，并依据当时可取得的最新外部评测与项目本地实绩做选择？
5. 如果能力缺失、未知、过期、数据源不可用或不存在合格候选，应该如何明确报告并降级？
6. 如何把本次终端的能力考核、选型理由和项目内观察留在本机，既可追溯又不跨终端共享？

### 1.2 非目标

- 不开发新的 Agent Runtime，不托管模型、不实现通用模型 API 网关。
- 不让 AgentOrch 的基础 CLI 依赖外网或某一家模型供应商。
- 不把某个固定模型名单、固定排行榜名次或固定分数写进角色契约。
- 不用排行榜代替真实运行时探测、权限检查、任务验证或代码审查。
- 不改变任务状态机、路径 / 资源锁、G1–G6 合并门或现有 C1–C4 能力探测语义。
- 不把本地反馈汇总成没有样本、窗口与任务类别背景的全局 Agent 排名。
- 不将终端私有记录提交到 Git、上传到远程服务或纳入发行包。

## 2. 架构原则

1. **先验证可用性，再比较能力。** 排行榜分数再高，也不能弥补运行时无法调用、模态不支持、工具不可用或权限不足。
2. **运行时、Agent、模型、权限是不同对象。** 一项能力只有在完整调用路径中可用，才可用于选型；模型支持某功能不代表当前 Agent 接口已暴露该功能。
3. **证据优先于声明。** 提示词、配置名称、模型宣传页或 Agent 自述可以作为待核实的线索，不能独立构成 PASS。
4. **未知即未验证。** UNKNOWN / STALE / NOT_RUN 不得折算成 PASS，也不得悄悄回退到先前模型或共享其他终端的记录。
5. **角色独立、职责明确。** Execution 执行实现；Reviewer 独立寻找问题；Master 保留计划、调度、审查和合并决策权。
6. **硬约束先于排序。** 任何加权得分都不能抵消模态、可调用性、权限或模型独立性等硬约束。
7. **动态数据必须带时间。** “最新”只能表示查询时实际成功读取到的数据，并附来源、版本（如有）与时间；不能证明新鲜度就写 UNKNOWN / STALE。
8. **离线治理仍然成立。** 外部模型数据是可选适配器；网络不可用时，现有任务治理与人工交接仍可运行。
9. **最小化本地数据。** 记录选型所需的事实、摘要和证据引用，不默认保存完整私有提示词、敏感代码、凭据或完整对话。

## 3. 角色契约

角色表示职责与验收要求，不绑定某个产品名、模型名或固定运行时。

### 3.1 Master Agent

Master 负责理解用户意图、规划项目、判断质量、协调角色并作出最终裁决。

- **多模态硬要求：** Master 模型与当前调用接口必须至少实际支持文本和图像输入。若未来任务要求其他模态，应将其显式列为任务硬要求，不得推定已有支持。
- **意图理解：** 区分明确要求、隐含目标、约束、开放假设和需要用户决定的事项。
- **规划能力：** 能结合项目章程、架构、依赖、允许 / 禁改路径、验证命令和交付风险形成可验收任务。
- **质量判断：** 不把执行者自述、模型自评分或单纯 CI 绿灯视为完整验收。
- **受控发散：** 可以提出替代方案、反例、风险和不同观点；必须区分事实、推断与建议，并说明依据和代价。
- **最终责任：** 处理 Reviewer 与 Execution 的争议，遵守 G1–G6；不能把最终裁决、批准或合并责任转交给执行者。

Master 不必在所有任务中使用最贵的模型。简单、边界明确的工作可使用满足硬要求的模型；重大架构规划、跨模块争议、长期未解决问题可按策略升级到更强的候选。

### 3.2 Execution Agent

Execution 的目标是以可控成本，按任务契约完成代码实现并提交可核验的交付证据。

- 编码、仓库理解、工具使用、测试执行和定位构建失败的能力。
- 高指令遵循度：不擅自扩大范围、不绕过限制、不改变冻结契约。
- 以合格交付成本、首次验收通过率、返工和回归缺陷综合判断性价比，不以每 Token 单价单独决策。
- 交付内容包括实际 Diff / 路径、命令与退出码、当前 head SHA、验收对应证据、未完成事项和剩余风险。
- 遇到需求歧义、越权需求、依赖缺失或无法复现的问题时停止并报告。

### 3.3 Reviewer Agent

Reviewer 的目标是独立发现错误并提出可验证的修复方向，而不是复述执行者的实现说明。

- 对照需求、设计契约、Diff、测试与当前 head SHA，主动寻找逻辑缺陷、边界条件、权限 / 安全风险、并发问题、迁移兼容性和缺失测试。
- 必须与 Execution 使用不同的底层模型 ID。优先使用不同模型家族，降低共同盲点；家族关系不明时标 UNKNOWN，不得宣称已实现家族级独立。
- “通常更强”以相关任务能力证据为判断依据：代码审查 / 缺陷检测表现优先于通用智力总分；不能仅凭价格、名称或供应商判断更强。
- 默认只读访问代码和审查材料；需要执行测试时只使用明确授权的只读或安全验证操作，不修改实现、不批准、不合并。
- 每项发现应包含严重程度、位置、触发条件、影响、证据 / 复现方法、置信度和建议修复方向；没有证据的疑点应标为待验证，而不是缺陷事实。
- 若连续多轮未能解决问题，Master 应重新检查原问题、修复方案和设计假设，必要时更换模型 / 家族或提出替代方案；达到现有修复上限后按现有契约阻塞，不无限循环。

不同温度、提示词、别名或同一底层模型的多个实例不构成模型独立性。

## 4. 能力模型与现有契约的关系

本设计不另建一套运行时能力定义。

- 运行时 spawn、隔离、wait/collect、终局分类继续以 [核心编排契约 §5](../../kit/orchestration.md) 的 C1–C4 为唯一权威。
- 更细的取消、文件 / 命令 / CI 权限、工具和测试环境、探测元数据继续沿用 [Runtime Capability Record](../../templates/runtime-capability.md) 的 C5–C8。
- 本文新增的是这些已登记能力如何被角色选择器消费，以及如何将模型评测和本地项目实绩纳入排序。
- 能力登记不授予权限。实际任务仍受 [AGENTS.md](../../AGENTS.md)、项目权限、允许 / 禁改路径和 G1–G6 约束。

每个候选的能力判断需区分：

| 维度 | 需要回答的问题 | 合格证据示例 |
|---|---|---|
| Runtime | 当前版本是否支持真实派发、隔离、等待与取回？ | C1–C4 的实测记录 |
| Agent 定义 | 候选是否存在、可定位、接受正确的任务输入？ | 运行时目录结果或显式配置 + 一次真实调用 |
| Model | 底层模型是什么，哪些模态和能力已确认？ | 精确模型 ID、供应商目录、适用基准和查询时间 |
| Tools / Environment | 文件、命令、测试、CI 与网络能力有哪些？ | C5–C7 的实测记录与限制 |
| Authorization | 此任务是否允许该候选读写指定路径、执行指定动作？ | 项目章程、任务路径和明确授权 |
| Evidence freshness | 证据是否属于当前 runtime / version / mode，是否仍可定位？ | 带时间与运行时身份的证据引用 |

单项状态应沿用现有模板的定义。本文中的 OBSERVED / INFERRED / UNKNOWN / STALE 是记录来源可信度的附加分类，不能替换 C1–C8 的 Verdict、Status 或现有状态语义。

## 5. Subagent 发现、可用性检查和缺失处理

### 5.1 发现顺序

1. 优先调用当前运行时正式支持的 Agent / Subagent 枚举或能力发现接口。
2. 如果运行时不支持枚举，读取明确配置的本地 Agent 注册表；每一项必须能映射到实际可调用的运行时标识和模型身份。
3. 对发现结果执行轻量、只读的可定位性与身份检查；不得仅凭目录文件、命名或提示词宣称完成了真实调用验证。
4. 对本次路由所需的能力引用最新的有效能力记录。运行时版本、执行模式、模型 ID、结果回收方式或权限边界变化时，对受影响能力重新探测。
5. 再把候选交给角色匹配器。发现结果本身不等于推荐结果。

### 5.2 能力缺失与交接

- **不能真实派发：** C1–C4 任一项不是 PASS 时，遵循现有契约降级为人工交接；Master 不声称已启动 Subagent。
- **没有 Execution：** 提示用户缺少执行角色，列出需要满足的能力和注册方式；存在可安全手动交接的方案时，生成任务包，但不伪称已派发。
- **没有 Reviewer：** 提示缺少独立审查角色；默认将任务保持在未完成审查的状态，不得由 Execution 自审代替。是否允许某类低风险工作使用人工审查，需由项目明确配置。
- **模型不可调用 / 权限不足：** 从本次合格候选中排除，并报告具体限制；不自动扩大权限。
- **候选身份不明：** 不得判为独立模型或合格角色，标记 UNKNOWN 并要求补充身份或重新探测。
- **没有合格候选：** 停止自动角色选择，向用户给出明确缺口、可选路径和需要的决定。可以提出创建 Subagent 建议，但不能自动创建或授权未经审核的 Agent。

## 6. 模型能力数据源与动态更新

### 6.1 数据来源

Artificial Analysis 模型排行榜是第一外部参考来源，但不是唯一的事实来源或单一排序标准。实现阶段必须核实可用的官方页面 / API、数据字段、许可与调用限制；本设计不预设某个 API 端点一定存在或永久免费可用。

按角色使用相关数据：

- Master：多模态输入支持、推理 / Agent 能力、规划与指令遵循相关评测。
- Execution：Coding Agent / 软件工程任务评测、工具使用、交付成功率、耗时与成本。
- Reviewer：代码审查、缺陷检测、安全审查、测试设计等直接相关的基准；通用推理结果仅作补充。
- 所有角色：当前可调用性、模型 ID、上下文要求、延迟、价格单位 / 数据时间和已知限制。

可以新增第二来源或项目自有基准，但各来源必须保留独立字段，不得把不同口径的分数直接当成可比值。

### 6.2 新鲜度与失败语义

每次查询记录数据源、数据集 / 指数版本（可取得时）、查询时间 UTC、数据发布日期（可取得时）、适用角色、单位、原始来源链接、限制和查询结果状态。

- 当次成功读取的当前数据才可称“本次查询的最新数据”。
- 网络失败、限流、结构变化、数据缺字段或无法判断发布日期时，明确报告相应状态；不能默默引用旧值并声称实时查询成功。
- 缓存只能用于离线降级。每份缓存需保留获取时间与新鲜度规则；过期即 STALE，不作为“最新评测”使用。
- 无外部数据时，系统仍可依靠已授权候选、能力实测和可用的本地证据运行；若硬约束因此无法确认，则停止自动选择或升级给用户决策。
- 基本治理命令不得因为排行站点不可用而失败；在线适配器作为可选组件运行。

## 7. 角色选择算法

采用“硬筛选 → 角色相关排序 → 可解释决策 → 结果记录”的顺序，不使用一个综合智力分掩盖硬约束。

### 7.1 硬筛选

先排除：

1. 当前运行时无法实际调用，或身份 / 版本无法确认的候选。
2. 任务所需的输入模态、上下文能力或必须的工具不满足者。
3. 所需读写 / 命令 / CI 权限不满足者，或必须依赖未授权动作的候选。
4. 能力记录缺失、过期或关键证据 UNKNOWN 的候选（可进入人工决策列表，但不能作为已验证的自动选择结果）。
5. 用作 Reviewer 时与 Execution 底层模型 ID 相同的候选。
6. 超出项目为本任务设定的预算、延迟或其他硬限制者。

Master 角色还必须通过文本 + 图像输入的真实路径检查。执行与审查若要求不同模型，先确定 Execution，再筛除与其同模型的 Reviewer。

### 7.2 排序信号

硬筛选通过后，按角色组合相关信号，而不是只按榜单总分：

- 相关专项基准的质量表现和适用范围；
- 项目内同类任务的实际交付证据；
- 成本、耗时、失败 / 返工和可复现性；
- 上下文、工具与环境匹配度；
- 评测数据的新鲜度、样本量和覆盖情况；
- 多样性价值：Reviewer 与 Execution 的底层模型差异、优先考虑的模型家族差异。

初始实现应采用可解释的分项排序 / 规则，不在没有校准数据时引入看似精确的权重或不可解释的总分。后续若需要加权模型，必须通过固定合成样本与项目实际反馈校准，并保留各分项与选择理由。硬约束始终优先于排序。

### 7.3 选择报告

每次选型至少写明：

- 目标角色、任务类别和需要满足的硬约束；
- 实际选中的 Runtime / Agent ID / Model ID；
- 备选候选及被排除的原因；
- 模型来源、指数 / 数据版本、查询时间和新鲜度；
- Runtime 能力记录引用、权限限制和未验证项；
- 选择理由（分项指标 + 项目内实绩，不只给单一总分）；
- 是否使用缓存 / 降级模式，是否需要用户决定；
- 决策时间与本次终端 scope ID。

任何模型排名或能力结论都应能够追溯到本次实际读取的来源。任务执行、审查与最终合并门仍按既有契约进行。

## 8. 每终端独立的本地 Markdown 记录

### 8.1 存储约束

所有角色发现、能力考核、模型数据快照、选择历史和项目内反馈都写在当前克隆的：

.local/agent-orch/<scope-id>/

每个终端 / Agent 会话只能使用其自身的 scope；同一仓库下的两个终端不得共享或覆写记录，也不从另一个终端的目录读取能力结论。该目录内容必须保持为 Markdown 文档，不使用 SQLite / JSON 作为记录事实来源。

仓库已有 .gitignore 规则会忽略 .local/*，仅保留 .local/README.md；.local 不在发行包清单内。本设计复用这些规则，不添加新的同步通道，不上传云端、不提交 Git、不打包到 Release。不得因本功能放宽忽略规则。受跟踪的 .local/README.md 只能写通用规则与示例，不得出现某台机器、真实终端、真实模型调用或个人信息。

### 8.2 Scope ID 发现规则

为保证“每个终端独立”而不是“每个仓库共用一份”，Scope ID 的解析顺序应冻结为：

1. 使用用户显式设置的 AGENTORCH_SCOPE_ID（可用于终端环境不支持自动识别的情况）。
2. 使用运行时公开提供、稳定且能区分独立会话的 session / terminal ID。
3. 在可交互 TTY 环境中，使用 TTY 身份的不可逆短摘要作为稳定 scope 标识；不得把原始终端路径写入文档。
4. 如果以上均不可用，不能把所有调用折叠到 default / shared 目录。必须提醒用户设置显式 ID，或创建一个新隔离 scope 并明确标记其身份来源为 INFERRED；在身份尚未稳定前，不得读取其他 scope 的历史数据或以其数据作自动选择依据。

Scope ID 只能用作本机目录选择，不作为权限授权。实现需验证目录名安全，拒绝路径穿越、绝对路径和路径分隔符；创建目录时不得覆盖已存在的其他 scope。

### 8.3 建议文件布局

以下都是普通 Markdown 文件；实际文件名和索引字段由实现任务依照此契约冻结：

.local/agent-orch/<scope-id>/
  README.md                 # 本 scope 的用途、身份来源与隐私说明
  agent-registry.md         # 已发现 / 手动配置的 Agent、Runtime、Model 映射
  runtime-capabilities.md   # C1–C8 记录引用与当前有效 / UNKNOWN / STALE 判断
  model-evaluation-snapshots.md # 外部评测来源、版本、查询时间与分项数据摘要
  selection-history.md     # 每次角色匹配、被选候选、替代项、排除原因、降级状态
  observed-performance.md  # 项目内任务类别、验收、返工、误报 / 漏报等摘要

不要复制 Runtime Capability Record 的 C1–C8 定义；这里应记录引用、文件定位与哪些能力当前有效。需要详细探测时，沿用既有模板的结构和语义，将记录副本写入当前 scope，并在本机记录之间建立相对链接。

### 8.4 写入、更新与隐私纪律

- 文件使用 UTF-8 Markdown，带生成 / 更新时间 UTC、scope ID、来源和状态；新记录优先追加，不静默伪造或改写历史事实。
- 重复执行时应幂等更新索引或新增选择事件，不得让两次不同选择覆盖成同一条历史。
- 只记录判断所需的最少字段、简短摘要和可定位证据；凭据、API Key、访问令牌、完整私有提示词、原始对话、客户数据和不必要的绝对路径禁止写入。
- 远程 URL / Issue / PR 等证据只有在本来就可公开或经授权时才能引用；公开仓库不得出现本地私有记录内容。
- 当前 scope 的能力记录不能被另一个 scope 自动继承。用户手动复制记录不代表其中的能力仍有效，必须重新核验适用的 Runtime / Model / version / mode。
- 若本地目录不可写或记录失败，应明确提示记录未写入；不能声称审计链已完成。按安全策略，可继续的只读建议与需落档的自动选择必须区分。

## 9. 项目内反馈与持续校准

外部排行榜是先验参考，项目内实测是补充证据，不可相互冒充。

- Execution 反馈可记录同类任务的首次验收情况、返工轮次、回归问题、交付耗时 / 成本（仅在真实可采集时）及样本量。
- Reviewer 反馈可记录其发现被确认的比例、误报、漏报（只有具备可核查的对照时才统计）、严重程度和是否阻止了回归。
- Master 反馈可记录规划遗漏、任务拆分返工、决策纠正与用户要求的偏离情况。
- 反馈按任务类别和时间窗口分组；不跨 scope 自动合并，不以样本过少的数据制作排行榜。
- 缺失数据标为 UNKNOWN / coverage，不填造 0；不能仅凭最终合并与否断言审查质量。
- 项目内观察只能影响同一 scope 的后续建议。是否把模型切换设为自动行为，需通过单独的实现与安全验收；首版优先输出可解释建议，由 Master 决策。

## 10. 失败、降级与人工决定

以下情况禁止自动选择或推进成“能力已验证”：

- C1–C4 未全部 PASS、能力证据过期，或执行实例结果状态不可判定；
- Master 的多模态输入链路未通过实际验证；
- 没有可调用的 Execution / Reviewer，或 Reviewer 与 Execution 的底层模型 ID 相同；
- 模型来源不可用且缓存已过期，而当前策略要求实时基准支持；
- 模型身份、评测数据口径、价格单位或数据时间不明，且这些信息会影响选择；
- 权限 / 工具 / 测试环境不满足任务要求；
- 当前 scope 无法可靠隔离，可能读取另一终端的能力或选择记录；
- 本地记录写入失败，且当前操作按策略必须留下选择证据；
- 按角色评测和项目内观察均无法形成有根据的选择。

输出应包括已确认事实、UNKNOWN / STALE 项、影响、降级方案和用户需要决定的选项。不能将“提示用户创建角色”与“运行时无法启动角色”混成同一种错误。

## 11. 分阶段实施计划

依赖关系如下。各阶段必须通过正常 Issue / 分支 / PR / 独立审查 / 合并后验证流程；在前置设计尚未合并时，不得开始依赖它的实现。

| 阶段 | 交付 | 主要路径（初步） | 依赖 |
|---|---|---|---|
| S0：设计冻结 | 本文、文档导航与 .local 用途说明；冻结本文核心规则 | docs/design/agent-role-discovery-and-model-selection.md、docs/README.md、.local/README.md | 无 |
| S1：本地 Scope 与 Markdown 记录基座 | 每终端独立 scope 解析、目录安全、Markdown 读写、脱敏与隔离测试 | 新增本地记录模块与测试；不动状态机 | S0 |
| S2：角色注册与能力匹配 | 运行时发现 / 显式注册表、C1–C8 记录复用、缺角色提醒、交接降级 | 新增角色目录适配器 / selector 与测试；必要的提示词入口变更单独授权 | S1 |
| S3：模型评测来源与动态选型 | Artificial Analysis 数据适配层（可用接口先行核验）、可追溯快照、角色硬筛选与解释性排序 | 新增来源适配器、缓存规则、selector 与 fixture 测试 | S0、S2 |
| S4：项目内评价与选型反馈 | 按任务类别记录本地实绩、误报 / 漏报与成本数据；缺失率和样本口径 | 本地 Markdown 写入与只读报告测试 | S1、S2、S3 |
| S5：完整合成回归与集成 | 正向与负向角色选择场景；C1–C4 失败、缺角色、数据过期、Reviewer 同模型、scope 冲突与写入失败 | 测试、场景说明、会话入口接线和发行前验收 | S1–S4 |

以上路径为规划建议，实施 Issue 必须在派发前重新核对最新 main、开放 PR 与路径冲突并收窄真实改动路径。不要通过一个巨大 Issue 同时改变能力契约、模型来源、运行时接线和回归体系。

## 12. 最小合成回归矩阵

| 场景 | 注入条件 | 预期结果 |
|---|---|---|
| 正向基线 | Runtime C1–C4 PASS；Execution 与 Reviewer 身份和权限有效 | 能生成可解释选择记录，不越过 G1–G6 |
| 不支持 spawn | C1 FAIL / UNKNOWN | 降级人工交接，不声称已派发 |
| 缺少 Execution | 注册表 / Runtime 中无合格 Execution | 明确提醒配置执行角色，保留任务未派发状态 |
| 缺少 Reviewer | 无独立 Reviewer | 提示阻塞审查，不接受执行者自审替代 |
| 相同底层模型 | Reviewer 与 Execution 的 Model ID 一致 | 排除该 Reviewer 候选 |
| 模型家族未知 | 不能确定家族关系 | 标 UNKNOWN；不声称家族级独立 |
| 模态不符 | Master 只能收文本，当前契约要求图像输入 | 硬筛选失败，说明输入链路缺口 |
| 外部数据过期 | 站点不可用且缓存过期 | 明确 STALE / UNKNOWN；不称为最新 |
| 候选超预算 | 估算或可用报价超出任务限制 | 排除候选并记录单位、时间和原因 |
| Scope 无法识别 | 无稳定终端 / 会话标识 | 不复用共享默认目录；提醒设置显式 ID 或新建隔离 scope |
| Scope 路径攻击 | ID 含绝对路径、分隔符或 .. | 拒绝，不读写目标外路径 |
| 本地写入失败 | .local 只读或磁盘错误 | 报告记录失败，不声称日志已落盘 |
| 无候选可用 | 所有候选都不满足硬约束 | 停止自动选择，列出缺口和需用户决定事项 |
| 项目反馈稀少 | 样本不足或对照缺失 | 只显示样本 / coverage，不生成误导性排名 |

合成回归应使用固定模拟数据和临时目录，不要求访问真实模型、真实凭据或真实项目私有数据；外部数据适配器的真实在线检查单独记录，并允许因网络环境而标 BLOCKED。

## 13. 验收要求与变更控制

- 本文与现有核心契约无冲突；字段、状态、G1–G6、C1–C4 和 C1–C8 各有唯一权威定义。
- 基础治理、任务登记与人工交接在离线条件下继续可用；外部排行榜不是基础 CLI 的强依赖。
- Scope 隔离必须通过同一工作树的两个模拟终端身份、显式 ID、无 TTY、ID 非法、权限错误和并发写入等测试。
- 模型选择必须通过固定 fixture 证明硬筛选优先于分数排序；没有合格候选时不能静默选出一个。
- Reviewer 独立性必须使用底层模型 ID 判定；“不同配置名”不能证明不同模型。
- 本地记录不会进入 Git 跟踪、发行清单或公开报告；记录缺失、无法写入或证据过期会如实报告。
- 文档内所有链接必须可解析；命令须在同一环境真实执行并记录退出码。无法运行的检查标记 BLOCKED / NOT_RUN，不能写 PASS。
- 涉及新外部 API、服务条款、网络依赖、权限模型或状态语义的决策，在实施前单独记录风险与所需授权。
