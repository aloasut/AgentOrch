# AgentOrch 设计目标

> 本文件是项目的**设计目标权威**：回答“为什么做、做到什么程度、边界在哪”。
> 阶段目标、任务顺序与状态不写在这里，见 [AGENTORCH_IMPROVEMENT_PLAN_2026-10.md](AGENTORCH_IMPROVEMENT_PLAN_2026-10.md)。
> 两者冲突时，以本文件的设计目标为准，停下对齐，不得各写一套。
> 字段、状态与合并门的定义只在 [AGENT-ORCHESTRATION.md](../AGENT-ORCHESTRATION.md)；本文件不重述规则。

## 1. 问题与目标用户

**要解决的问题。** AgentOrch 管理的是“多 Agent / 多会话推进同一个软件项目”这件事。当前这类流程的正确性主要依赖执行者与审查者的自觉，具体表现为四类失效：

- **协作失序**：不清楚谁在做哪个任务、改了哪些文件，两处改动是否撞在同一路径上。
- **状态丢失**：换会话、换机器或上下文被截断后，只能靠聊天记忆猜进度。
- **自批自合**：执行者自己宣布完成、自己批准、自己合并，审查门形同虚设。
- **证据不可核验**：只报“已完成”，不给当前 head SHA 上的命令、输出与退出码；或用旧结论、CI 绿灯代替逐条验收。

**目标用户。** 一位操作者或一个小团队，用多个 Agent / 多个会话推进同一个软件项目；愿意使用 Git 分支与 Worktree，并接受“执行者不自批、合并由 Master 决策”的约束。规模再大、需要完整账号权限体系与合规审计的组织不在目标用户内。

## 2. 设计目标

系统应具备的能力与必须守住的不变量。每条都可以判断“做到什么程度”，不需要读阶段细节：

1. **任务可核验**：每个任务有唯一 ID、单一可验收目标、允许 / 禁改路径、逐条验收标准、依赖与验证命令；每条验收标准至少对应一条绑定当前 head 的证据条目。
2. **状态可恢复**：任务状态只由任务载体（`local` 任务库 / `github` Issue 与 PR）和 Git 决定；任何新会话都能在没有聊天记忆的情况下重建真实进度。
3. **门禁不可绕过**：合并前必须逐门通过，证据绑定 head SHA；head 变化即令旧批准失效。角色权限、审查门与测试强度不因底座不同而降级。
4. **权限不混用**：Master / Execution / Reviewer 职责固定；执行者不自批、不自合、不声明自己已通过验收。底座切换单向、一次性、禁止双写。
5. **底座可互换**：`local` 与 `github` 共用同一份核心契约，只有任务载体与证据来源不同；`edition` 只有唯一权威来源，缺失或非法时失败关闭，不猜默认值。
6. **主张必须可证**：文档里写的命令要真跑并记录退出码；能力、指标与漂移结论要么链接真实证据，要么标为未知 / 过期，不用提示词自述代替执行结果。
7. **计划分层**：设计目标与阶段计划各守一层——状态变化只改阶段计划，设计目标只随方向调整而变，二者冲突时以设计目标为准并停下对齐。
8. **套件可复用**：模板与提示词保持项目无关，纯标准库、零第三方依赖；结构自检清单与发行包清单同源，不维护第二份文件列表。

## 3. 设计原则

冲突时的取舍顺序：

- **单一权威**：字段名、状态取值、门禁语义只在一处定义，其余文档只引用不重述。
- **证据先于结论**：没有当前 head 上的命令、输出与退出码，就不算完成；历史结果与 CI 绿灯都不能替代逐条验收。
- **失败关闭**：配置非法、证据缺失、锁冲突、路径越界时停止并报告实际观察，不用默认值继续。
- **最小流程**：只增加能降低返工或防止误报的结构；不为了模板完整而过度文档化。
- **只读诊断**：涉及下游项目的检查只读，不自动覆盖；漂移由各项目自己的任务修复。
- **测试强度不可降**：修绿只能修实现，不能删断言、放宽验收、跳过检查或把失败检查移出配置。
- **小步交付**：一个任务一个可独立验收的结果，一条分支一次独立审查。

## 4. 范围与非目标

**范围。**

- 与底座无关的核心契约：角色权限、状态机、合并门、证据标准、能力探测。
- `local` 与 `github` 两个底座的任务载体、锁机制与启动 / 执行 / 审查提示词。
- 任务包、计划、设计契约、审查与验收模板。
- 纯标准库 CLI（任务库、路径锁、结构自检、发行打包）与合成回归场景。

**非目标。**

- 不开发托管式调度服务、SaaS 控制台或新的 Agent Runtime。
- 不引入任何第三方 Python 依赖、包管理器或构建步骤。
- 不把套件变成某个具体产品的专用配置集合。
- 不自动向下游项目同步或改写文件；不把“哈希不同”直接解释成应覆盖的漂移。
- 不宣称 GitHub Issue 评论具备数据库式的原子互斥能力。
- 不把提示词里的能力声明当成真实执行能力，不把未执行的检查写成已通过。
- 不以“子任务全部关闭”单独作为阶段完成标准。

## 5. 全局约束

- **规则分层**：Core Contract（状态机、门禁、证据、能力、锁生命周期）→ Project Profile（底座、分支、验证命令、路径范围、隐私）→ Project Extension（项目专有设计门、版权与安全要求、人工批准条件）。同一字段只定义一次。
- **技术栈**：Python 3 标准库；CLI 只管理任务状态与路径锁，不启动模型、不写业务代码、不自动合并。
- **运行环境**：Windows + Git Bash 实测；CI 为 `ubuntu-latest` + Python 3.12 / 3.13。其他操作系统与 shell 未验证，命令需按环境调整。
- **隐私**：不提交密钥、令牌、个人路径与私有数据；机器特有信息放 `.local/`，永不入库、永不打包。
- **兼容与变更纪律**：状态机、门禁、锁生命周期、`edition`、`retry_cap` 的语义变化必须先冻结契约、再实现、再演练；破坏兼容或不可逆迁移进入人工决策。

## 6. 可度量的全局验收

以下检查必须能在当前 head 上重复执行；任一失败即视为系统未达成设计目标：

- [ ] `python scripts/validate_kit.py` 退出码 0，且打印的必需文件数量等于 `REQUIRED` 的真实长度。
- [ ] `python -m unittest discover -s tests` 退出码 0，没有用 skip / xfail 顶替断言。
- [ ] `python -m py_compile scripts/orchestrator.py scripts/validate_kit.py` 退出码 0。
- [ ] `python scripts/build_release.py` 自检 a–f 通过，包内文件集合与 `REQUIRED` 完全一致。
- [ ] 交付任务的每条验收标准都有证据条目；`FAIL` / `NOT_RUN` / `BLOCKED` 状态的证据不会被计为通过。
- [ ] 两个底座的登记检查在 PR 的当前 head 上全绿；head 变化后在新 head 上重跑，不复用旧结果。
- [ ] 计划分层可判定：`docs/PLAN.md` 不含阶段顺序与任务状态内容，阶段计划不含第二套门禁或证据定义。
