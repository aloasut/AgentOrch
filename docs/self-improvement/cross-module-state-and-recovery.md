# 跨模块状态 / 并发 / 恢复：任务验收规则（R1–R6）

> **定位**：本文件是**增量验收检查点**，不是第二套契约。任务状态机、路径 / 资源锁、证据矩阵与合并门 G1–G6 **只在** [`kit/orchestration.md`](../../kit/orchestration.md) 定义；字段名、取值与判定规则只在其中 4.1 节定义。本文件只引用、**不复制、不改写**。
> **适用**：涉及共享可变状态（manifest / 索引 / 缓存 / 计数）、锁文件、备份与回滚、多阶段提交、目录遍历的任务。
> **证据来源**：下游项目的公开 Pull Request。本文件只引用链接与自行撰写的泛化摘要，不复制其代码、业务数据、目录结构或受版权文本；所有 fixture 均为合成数据。

## 1. 怎么用

1. 任务包 / Issue 的 `invariants`、`negative_cases`、`migration_cases`、`integration_paths` 按 [4.1 节](../../kit/orchestration.md)填写；本文件只说明**这些字段应覆盖哪些表面**，不新增字段。
2. 与共享状态有关时，`integration_paths` 里必须有**调用点清单**（见 R2）；`negative_cases` 里必须有**最终状态断言**（见 R3–R6），不能只写“返回错误”。
3. 小任务确实不涉及这些表面时写 `N/A: <理由>`，理由必须说明“为什么该表面对本任务不存在”，不得只写 `N/A`。
4. 不适用不等于免检：标为 `Reviewer 判定` 的条目**没有**自动检查，Reviewer 必须逐条给结论；不得把它们写成“已被静态分析覆盖”。

## 3. 规则明细

每条规则的“最小证据”是**最低**要求：只写“测试通过”不算证据，必须给出可核对的状态。

### R1 模块分层与旧行为兼容

- **要求**：入口 / 注册 / CLI 层只做参数解析与路由；职责落在模块内。重构后旧调用路径的外部行为（输出、退出码、错误类型、持久化格式）保持不变。
- **最小证据**：`invariants` 写明“旧行为不变”的具体可观察量；`integration_paths` 列出被改动的调用方与被依赖方；证据矩阵中至少一条是**旧路径**的回归测试，一条是**新路径**的测试。
- **负向案例**：只跑新路径；用“文件更少 / stub 更多”当作高内聚证明；把入口层的新分支直接写成业务逻辑而不说明归属。
- **`Reviewer 判定`**：模块职责划分是否合理没有自动判据；`responsibilities` 是否名副其实、是否把业务逻辑塞回入口层，只能人工判断。

### R2 共享状态全调用点清点

- **要求**：列出全仓库对同一共享状态（文件、manifest、索引、缓存、计数器）执行**读 → 改 → 写**的每个调用点，并逐个说明其并发保护范围；只保护其中一个调用点视为未完成。
- **最小证据**：`integration_paths` 中的调用点清单（每个调用点 → 保护手段 → 为什么足够）；负向测试必须制造**交错**并断言最终状态（丢更新 / 计数错误），而不只是“某次调用失败”。
- **负向案例**：只测主路径；清单漏掉后台 / 自动保存 / 重试等次要入口；用“调用点很少”替代清点。
- **`Reviewer 判定`**：静态分析**不能**可靠证明“全仓库调用点已穷尽”。本仓库的合成检查（场景 C7）只覆盖合成模块里的单一辅助函数；真实项目的动态导入、插件、反射与字符串路由都可能绕过，必须由 Reviewer 对照清单人工核对，并明确写下未覆盖的入口。

### R3 恢复 / 回滚的完整状态契约

- **要求**：回滚的定义是“回到基线状态”，不是“恢复我记住的文件”。结束时（a）基线中存在的文件内容一致，（b）基线之后新增的文件与目录全部消失，（c）失败操作自身的临时产物不残留。
- **最小证据**：比较**最终文件树**（路径集合 + 内容摘要）与基线，而不只是返回值或错误类型；证据里写出差异清单（或“差异为空”）。
- **负向案例**：只验证“返回 Err”；回滚后目录树残留备份外新增文件；回滚把无关目录一起覆盖；只比较文件数量不比较内容。
- **`Reviewer 判定`**：哪些基线快照真正覆盖全部状态（内存缓存、外部服务、数据库）无法由文件树断言证明；Reviewer 需要确认“基线”的定义覆盖了本任务的其他持久化面。

### R4 锁生命周期不被业务回滚破坏

- **要求**：锁的创建 / 释放 / 失效与业务数据的回滚**解耦**：业务回滚不得删除活动锁，也不得把旧锁复原成已失效的持有者。互斥在恢复路径上仍然有效。
- **最小证据**：负向测试必须同时给出（a）锁文件在回滚后的存在性，（b）第二个写入者能否取得锁（互斥是否真的失效），（c）正常释放后可再次获取。只断言“锁文件还在”不足以证明互斥。
- **负向案例**：锁文件放在被回滚的目录树内；回滚恢复整个根目录导致活动锁被删；回滚把过期锁复原后继续当作有效锁；锁释放失败被忽略。
- **`Reviewer 判定`**：跨主机 / 网络文件系统上的锁语义、崩溃瞬间的锁状态无法在本套件离线验证；涉及这些场景时标 `UNKNOWN` 并交人工确认。

### R5 阶段化失败语义（部分提交）

- **要求**：多阶段写入失败时，报告必须写明：已完成阶段、失败阶段、遗留副作用、备份 / 回滚位置、以及“是否自动回滚”。没有执行回滚就不得写“已完整回滚”。
- **最小证据**：报告中四个字段齐全，且**与磁盘 / 状态核对一致**（失败阶段之后的副作用确实不存在，之前的确实存在）。负向测试要构造“声明完整回滚但实际残留”的报告，并用最终状态否证它。
- **负向案例**：部分提交后宣称完整回滚；只报告异常不报告副作用；备份位置缺失导致无法恢复；把“进程退出码非零”当作“已回滚”。
- **`Reviewer 判定`**：报告字段与真实副作用的**语义**一致性（例如“副作用”是否穷尽）需要人工核对；自动检查只能证明所列副作用与文件树矛盾或一致。

### R6 错误不得静默吞掉 / 最小复现优先

- **要求**：（a）目录遍历、清理、回滚等步骤的错误必须可见：要么失败，要么在报告中带明确理由与受影响条目；（b）修缺陷前先留下可复现证据（失败的测试、最小脚本或源码级定位），再决定方案。
- **最小证据**：负向测试给出“跳过条目但仍声称成功”的矛盾报告，并被 `processed != total` 之类的计数否证；修复后同一输入产生可诊断错误并指名条目。
- **负向案例**：`except OSError: pass`；把跳过当作“尽力而为”却不计数；先写“修复”再补测试；用降低断言换取绿色。
- **`Reviewer 判定`**：“最小复现是否真的先于修复”是过程事实，只能由 Reviewer 从提交顺序、PR 时间线或复现脚本判断，不能由静态检查证明。

## 5. 已知限制（不得声称已覆盖）

1. **调用点穷尽性**：没有静态能力可以证明“所有读改写调用点都已找到”。场景 C7 的调用点清单是对**合成模块**的单一辅助函数做 AST 检查，只证明“清单能定位一个未加锁调用点”，不证明真实仓库的完整性。此项永久保留为 `Reviewer 判定`。
2. **R1 没有合成场景**：模块分层与“旧行为不变”无法用一套项目无关的合成场景证明；它依赖 `invariants` 的写法、旧路径回归测试和（可选的）Architecture Contract 检查（[契约](../architecture/architecture-contract.md) / [检查器](architecture-checker.md)）。静态指标不得当作高内聚证明。
3. **无法离线验证的语义**：跨主机锁、崩溃瞬间状态、外部服务一致性、真实时序竞态，本套件只能给出单机单进程的合成交错。出现这些场景时按 `UNKNOWN` 处理并交 Reviewer。
4. **外部项目**：本文件不对任何下游项目做过真实数据或端到端运行；场景只证明本套件自身的检查点会拒绝错误输入。
5. **fixture**：全部为运行时生成的合成数据（合成目录树、合成 manifest、合成模块源码字符串），不含真实业务文件、个人信息或凭据。

## 6. 变更规则

- 本文件只增加验收检查点；与 [`kit/orchestration.md`](../../kit/orchestration.md) 冲突时以核心契约为准，并停下登记冲突，不得各写一套。
- 新增 / 修改场景必须同步更新 [场景目录](../testing/delivery-regression-scenarios.md) 与 `scripts/run_delivery_scenarios.py` 的注册；`tests/test_run_delivery_scenarios.py` 会检查场景 ID 是否在文档中登记。
- 修改模板中的检查项必须保留“小任务可写 `N/A: <理由>`”的出口；不得把不适用的小任务判为失败。
