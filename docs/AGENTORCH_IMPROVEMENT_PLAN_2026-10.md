# AgentOrch 可靠性交付升级实施蓝图

- 版本：v1.0
- 日期：2026-10-22
- 状态：实施计划；以 GitHub Epic #1 与子 Issues 为任务真相
- 适用范围：AgentOrch 核心规则、local/github edition、任务模板、验证脚本和发行机制
- 原则：不引入第三方依赖，不开发 Agent Runtime，不自动覆盖下游项目，不弱化既有安全门

## 1. 执行摘要

本轮升级不重新发明多 Agent 工作流，而是补足现有流程中依靠执行者/审查者自觉完成的部分，把关键规则转成结构化字段、可重复的检查、故障演练和可追溯报告。

三个近期项目给出的主要输入：

- **AgentMgr：治理状态和权限边界。** 授权撤销、任务重试/租约、审计上下文和审批可见性等路径，需要负向、竞态和跨接口验证，而不只验证正常请求。
- **TalkDND：规则版本、旧数据和发行可靠性。** 2014/2024 规则目录隔离及角色护甲迁移问题说明，功能新增需要考虑旧数据、幂等重跑、版本隔离和回滚。
- **NotDND：系统级不变量。** 六角格战斗的设计冻结与 E2E 工作，以及战斗时钟、行动者权限、坠落事件、测试运行器等在办问题说明，模块测试通过不代表完整交互闭环正确。

这些项目只作为经验来源。本次 AgentOrch 测试将使用合成 fixture，不直接复制产品仓库的内部数据、私有信息、凭据或受版权保护内容。

## 2. 当前基线与待解决问题

AgentOrch 已拥有以下核心资产：

- local 与 github 两种底座，核心治理契约共用；
- 任务状态机、依赖、活动路径锁和异常锁保留策略；
- G1–G6 合并门、head SHA 绑定、当前 head 验证和合并后验证；
- C1–C4 运行时能力探测，以及能力不足时降级为多会话交接的原则；
- 任务包、计划、审查与通用验收模板；
- 纯 Python 标准库实现与套件结构校验。

本轮不重复建设这些能力，重点处理以下差距：

1. G1 要求逐条证据，但任务模板还没有统一的机器可检查证据映射、负向场景和跨模块不变量结构。
2. 复杂项目需要 Design Contract 与 Milestone Audit，但阶段检查较依赖 Master 阅读多处文档并凭上下文汇总。
3. 路径锁无法表达测试数据库、共享构建环境和共享生成产物等具名资源冲突。
4. Bootstrap 要求非法 edition 失败关闭，而 CLI 配置读取会对若干非法/缺失值回退默认值；项目底座选择与 local CLI 配置边界需要说清并测试。
5. 下游项目复制套件后，缺少可靠的版本清单/漂移诊断；自动同步又可能覆盖项目特有政策。
6. C1–C4 是必要的运行时基础能力，但缺少面向交付物类型、权限、环境与证据的新鲜度登记；流程指标也缺少统一口径。
7. 套件自身需要能反复演练跨模块失败场景，不仅在文档中要求 Agent“检查”。

## 3. 目标与非目标

### 3.1 目标

- 每项重要验收标准可映射到当前 head 上的验证方法和证据。
- 设计冻结内容、用户决策、契约变化与受影响任务可追溯。
- 阶段收口能够列出阻断项、非阻断加固、可选增强和待人工决策项。
- 文件锁与具名资源锁各司其职；冲突、租约和异常恢复语义明确。
- 项目级 edition 选择只有一个权威来源；非法配置不能静默降级到另一执行模式。
- 能识别 AgentOrch 版本和核心契约漂移，同时保留下游扩展，不自动改写下游。
- 运行时能力与交付指标基于实际证据，不凭提示词或 Agent 自述。
- 建立 local/github 共同核心、底座特有行为的合成回归和可控失败验收。

### 3.2 非目标

- 不开发托管式调度服务、SaaS 控制台或新的 Agent Runtime。
- 不引入第三方 Python 依赖。
- 不将 AgentOrch 变成产品专用的 AgentMgr/TalkDND/NotDND 配置集合。
- 不将“哈希不同”自动解释成应覆盖的漂移，不自动向下游同步或修改文件。
- 不宣称 GitHub Issue 评论具备数据库式原子互斥能力。
- 不把提示词中的能力声明当成真实执行能力，不将未执行检查写成已通过。
- 不以“所有 Issue 已关闭”单独作为阶段完成标准。

## 4. 架构与演进规则

### 4.1 三层配置

1. **Core Contract**：状态机、角色权限、证据标准、G1–G6、能力探测及锁生命周期的权威规则。
2. **Project Profile**：底座、默认分支、测试命令、路径范围、环境、隐私和项目级资源锁。
3. **Project Extension**：项目专有设计门、版权规则、安全要求与人工批准条件。

通用字段只定义一次；edition 说明如何保存任务状态与获取证据，不复制另一套核心语义。

### 4.2 证据原则

- 每个结论都绑定当前 head SHA；head 变化后，受影响的测试与批准失效。
- 将验证分为“未运行、运行失败、通过、被阻塞、不适用（有理由）”等状态，未运行不得默认为通过。
- 证据应包含来源、命令/测试、退出码/结果、环境、时间、SHA 和已知限制；避免存储无必要的原始提示词、私人数据或凭据。
- CI 绿灯只证明配置的检查通过；仍须逐条对照验收标准及系统不变量。
- 真实项目经验作为场景描述，不代替当前 AgentOrch 的可复现测试证据。

### 4.3 安全变更纪律

涉及状态机、授权、路径锁或资源锁生命周期的变化，必须先冻结契约，再实现，再进行故障演练。遇到不可逆迁移、已有数据库兼容性、角色权限和外部依赖变更时进入 `NEEDS_HUMAN_DECISION`。本轮默认保持标准库依赖。

## 5. 分阶段路线

### Phase A — 契约和验收基础

交付：
- 任务包证据矩阵、负向场景、迁移场景与跨模块不变量字段（Issue #2）。
- Design Contract 与 Milestone Audit 模板（Issue #3）。
- edition 权威来源和 fail-closed 语义修正（Issue #4）。
- 共享资源锁设计契约（Issue #5）。

出口条件：
- 核心字段、证据与状态语义有唯一权威定义。
- 两个底座字段含义一致；不同之处只在载体和证据来源。
- 资源锁契约包含并发、崩溃、租约过期、强制解锁和恢复行为。
- 配置缺失/非法行为可通过测试证明；不破坏现有 local 状态库。
- 所有文档新增内容通过规则包校验；命令证据来自真实执行。

### Phase B — 调度、漂移和能力可观测性

交付：
- 按冻结契约实现具名资源锁及冲突诊断（Issue #6）。
- 发行清单及只读套件版本/核心契约漂移诊断（Issue #7）。
- 运行时能力登记、度量定义及最小只读报告（Issue #8）。

出口条件：
- 锁竞争不会产生半套锁、重复所有权或静默释放。
- 漂移诊断不修改目标仓库；下游特有文件被识别为扩展而不是自动覆盖对象。
- 能力清单区分支持、不支持、未知与过期，且链接到真实测试证据。
- 指标定义精确、可复现，并显式报告缺失数据与样本量。

### Phase C — 合成回归与发布验收

交付：
- 四类合成场景：治理/授权、数据迁移/版本隔离、跨模块闭环、编排底座与证据失效（Issue #9）。
- 将新检查纳入通用验收程序与 README。
- 在隔离环境中进行可控失败演练，并保存最终证据。

出口条件：
- 正向控制组和负向失败组均覆盖；场景可重复运行，不依赖真实密钥、外部模型、外部业务服务或私有数据。
- local/github 核心验收语义一致；无法离线验证的 GitHub 特有动作须明确标为待验证/阻塞。
- 旧 SHA、证据缺失、锁冲突、异常测试终止和待人工决定项不能被误报为 VERIFIED。
- 完整测试在当前 head 实际通过，或未通过项有明确阻塞记录；没有以历史 CI 或旧 commit 代替。

## 7. 跨项目的合成回归矩阵

| 场景组 | 来自项目的经验模式 | 合成失败注入 | 预期拦截 |
|---|---|---|---|
| G — 治理/授权 | AgentMgr 的 grant 撤销、重复写、审计与任务重试 | 过期/撤销授权、重复提交、审计关联缺失、并发状态变化 | 负向验收失败；授权/审计证据不完整不能通过 |
| M — 迁移/版本 | TalkDND 的旧角色数据与规则版本隔离 | 旧格式升级、迁移重跑、目标版本混用、写入一半后故障 | 幂等/回滚验收失败时阻断；明确迁移证据 |
| X — 跨模块闭环 | NotDND 的战斗状态、时钟、单位所有权与事件链 | 契约规则未接线、越权对象 ID、事件屏障遗漏、非断言异常 | 端到端/不变量检查失败；测试仍输出总结报告 |
| O — 编排器本身 | AgentOrch 的底座、锁和证据门 | 非法 edition、重叠资源锁、旧 SHA、缺证据、超过修复上限 | 不能进入 APPROVED/MERGED/VERIFIED；原因可定位 |

所有 fixture 都只模拟数据结构与行为，不复制三个产品项目的专有业务数据或受版权文本。至少保留一个通过控制组，避免回归套件只会报告失败。

## 8. 统一定义的阶段与 Issue 出口

### Issue 出口

每个 Issue 在关闭之前都应包含：
- 与 Issue 对应的变更文件及路径范围；
- 当前 head SHA；
- 每条验收项对应的测试/命令和实际结果；
- 负向场景、迁移/兼容场景或“不适用理由”；
- 风险与未完成项；
- 独立审查结论；
- 合并后验证命令、退出码与证据来源。

### 阶段出口

阶段结束不能仅依据子 Issues 全部关闭。Master 应以 Milestone Audit 汇总：
- 必需功能和不变量是否逐项验证；
- 安全/隐私、迁移兼容性和回滚；
- 端到端完整路径与错误恢复；
- 性能基线（只有有实际测量才下结论）；
- 已知缺口分类及其后续 Issue；
- 当前主分支 SHA 上的完整检查结果。

只要存在 BLOCKING，阶段不得标为完成。存在 NON_BLOCKING_HARDENING 时可根据项目章程继续，但要明确风险、负责人/跟踪 Issue 和接受依据。存在 NEEDS_HUMAN_DECISION 时保留阻塞，不代替所有者做决定。

## 9. 回退策略与风险处理

- 文档/模板变更：通过单独分支/PR 回退；不要删改历史记录。
- 资源锁实现：先兼容既有路径锁；新资源锁异常不得自动解锁全部活动任务。状态不明先阻断并人工复核。
- 配置行为：对旧合法 local 配置保持兼容；迁移需要单独测试与记录。不支持的 github CLI 行为明确失败，不冒充可执行。
- 版本漂移：诊断只读，不自动覆盖；修复由项目各自的 Issue/PR 完成。
- 指标：缺数据标 UNKNOWN/coverage，不用估算值填补。
- 测试：不得通过删除断言、放宽验收、吞掉异常或把检查挪出配置来“修绿”。
- 发布：manifest、包内容、脚本及模板校验通过后才能发布；发布说明标出新增功能、兼容性边界和未验证能力。

## 10. 总体验收清单

- [ ] Core Contract、Project Profile、Project Extension 的归属有明确说明。
- [ ] local/github 使用相同的任务与审查语义。
- [ ] 任务证据矩阵、Design Contract、Milestone Audit 模板齐全。
- [ ] 配置缺失、非法、损坏和未支持的底座行为均有测试。
- [ ] 路径锁与具名资源锁职责明确，且有并发/故障演练。
- [ ] 漂移诊断只读，manifest 可重现、哈希可复核。
- [ ] Runtime 能力和质量指标基于真实来源并标明缺失数据。
- [ ] 四类合成回归场景含正向组、负向组、证据和清理步骤。
- [ ] 当前 head 的规则包验证、单元测试、发行包检查全部实际执行。
- [ ] 主分支合并后重跑完整验证；记录命令、退出码、SHA、审查结论与遗留风险。
