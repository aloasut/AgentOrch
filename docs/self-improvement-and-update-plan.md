# 自我完善与安全更新机制规划

- 文档版本：v1.1（契约冻结状态说明更新）

- 上位设计目标：[PLAN.md](PLAN.md)
- 阶段计划：[implementation-plan.md](implementation-plan.md)

## 1. 目标与范围

本计划增加两项由自然语言触发、但必须通过可核验工作流执行的能力：

1. **“进行自我完善”**：从已登记、获准访问的 AgentOrch 下游项目中收集可泛化的研发经验，提炼重复问题与已验证教训，形成改进方案，拆解任务，按现有 AgentOrch 规则派发执行，最后独立审查、运行测试并报告结果。
2. **“更新 AgentOrch”**：从官方 AgentOrch GitHub Releases 获取最新版，核验版本、清单与文件完整性，与当前项目已安装的套件版本和本地改动进行三方比较；自动整合无冲突更新，保留项目配置与扩展，遇到冲突停止并提供逐文件方案。

首批学习来源为：
- TalkDND：`https://github.com/ctrlshiftaltdel/TalkDND`
- AgentMgr：`https://github.com/ctrlshiftaltdel/AgentMgr`

来源必须是可配置登记项，不得把两个项目写死在代码逻辑中。用户未来可以添加、停用或移除来源。不能访问的项目、缺失的 CI/PR 证据和未执行的验证必须明确标记为 UNKNOWN / NOT_RUN；不得根据聊天印象填补。

本计划同时纳入此前建议的**项目可配置架构契约、依赖边界检查、跨模块不变量验证与架构变化指标**。这些是自我完善所要使用的质量门，不应单独发展成另一套与 AgentOrch 任务 / 证据 / 合并门并行的治理体系。

## 2. 明确的交互目标

在套件安装项目里，用户可直接对 Agent 说：

### 2.1 “进行自我完善”

推荐同义表达包括“自我完善”“根据其他 AgentOrch 项目的经验改进本项目”“总结近期开发教训并推进改进”。入口应把这些表述路由到同一流程：

1. 恢复项目真实状态：读取项目配置、规则、任务载体、Git status、当前 head SHA、最近任务和尚未解决的阻塞。
2. 读取有效的经验来源登记表，收集来源项目自上次成功扫描以来的新 PR、Issue、审查结论、提交和 CI 证据；首次执行时按配置的回溯范围读取。
3. 从证据中提取候选教训，检查问题是否真实、是否已修复、是否有可复现证据、为何现有机制未阻止它。
4. 对候选教训分类、去重、评估适用性和信心，区分“已证实缺陷”“观察到的流程问题”“待验证假设”“仅适用于来源项目的特例”。
5. 将可泛化的教训映射到本项目已有规则、代码与测试，判断现有能力是否已经覆盖；不要因为来源项目新增了某种机制就重复造轮子。
6. 生成改进提案和影响分析，列出目标、非目标、根因 / 证据、预期收益、复杂度成本、允许修改路径、验收标准、负向测试、迁移 / 回滚方案及尚未解决的决策。
7. 建立或更新阶段计划和 GitHub Issues / local 任务记录，明确依赖、允许路径、负责角色、验证命令和当前 head 基线。
8. 按 AgentOrch 既有规则安排 Execution Agent 实现；路径不冲突且依赖满足的任务可以并行，同一 Worktree / 测试资源冲突时必须串行。
9. 由 Master / Reviewer 独立检查 diff 与证据，运行与当前项目配置匹配的测试、架构检查、套件自检和回归场景；head 变化后重新验证。
10. 汇报已完成、已创建任务、阻塞、未验证能力、当前 SHA 和每项证据的链接。没有实际执行的项目不得标为通过。

该短语表示启动完整工作流，而不表示无条件批准一切改动。常规、可回滚、低风险改进可在既有权限内自动规划和执行；改变安全边界、权限模型、状态机 / 锁语义、数据格式、外部依赖、隐私边界、兼容性或不可逆行为时，必须进入 NEEDS_HUMAN_DECISION。默认不自动合并 PR、不绕过 Master 审查门、不推送未经授权的破坏性更改。

### 2.2 “更新 AgentOrch”

同义表达包括“升级 AgentOrch”“把项目中的 AgentOrch 更新到最新版”。入口应：

1. 确认项目根目录、当前 edition、已安装版本 / Format、当前 Git 分支和工作区状态。
2. 若工作区存在未提交改动，先列出并保全；不能自动 stash、丢弃或覆盖。优先在任务专属分支 / Worktree 中继续，无法安全创建隔离工作区时停止并报告。
3. 从官方仓库 `ctrlshiftaltdel/AgentOrch` 的 Releases 检索最新稳定版。不得将任意第三方 URL、issue 评论或未经核验的分支内容视作正式发行包。
4. 将发行包下载到项目外临时目录，验证版本、压缩包成员路径、MANIFEST、文件集合、大小与 SHA-256；拒绝路径穿越、意外符号链接、清单不一致和无法核验的包。验证失败时不安装。
5. 使用已安装套件的旧 MANIFEST / 版本清单作为基线，对当前文件、旧上游版本和新发行版做三方分类。
6. 自动应用可证明无冲突的上游更新；永不直接覆盖项目自己的 `docs/PROJECT.md`、`docs/PLAN.md`、项目源码、项目测试、`ORCHESTRATION-PROJECT.md` / 旧版配置、项目扩展和未登记文件。
7. 对双边修改、上游删除、重命名、旧配置迁移、公共契约破坏或来源基线缺失生成逐文件冲突报告；不自动删除或覆盖。Agent 可以提供合并补丁建议，但冲突解决须依据项目所有者的授权规则。
8. 运行升级前备份、迁移检查、规则包结构校验、单元测试、漂移诊断、打包自检与项目配置的验证命令；记录升级前后版本、head SHA、文件分类、命令与退出码。
9. 生成 PR（GitHub edition）或任务 / 分支交付包（local edition）；除非项目规则和所有者明确允许，不直接改写主分支、不自动合并。
10. 对不支持的旧 Format、缺少基线 MANIFEST、发行包验签 / 校验信息不足或需要人工决定的情况，失败关闭并提供手工迁移路径。

**默认行为是“安全地准备整合”，不是“解压覆盖”。** 无冲突变更可以自动落到隔离分支；冲突必须显式显示，用户可逐文件决定保留、本地合并、采用上游或延后。

## 3. 可配置的经验来源注册表

### 3.1 设计要求

新增单一权威来源注册表（建议 `docs/self-improvement/sources.json`，最终结构由契约 Issue 冻结），由 AgentOrch 本体维护并随规划 / 发行工作流使用。注册表最少包含：

- schema_version；
- source_id（稳定 ID）；
- repository（规范化 GitHub owner/repo）；
- enabled；
- source_type / access_mode（公开、经授权的私有源或暂不支持的源类型）；
- evidence_scope（PR、Issue、review、commit、CI；默认最小必要范围）；
- lookback / last_successful_scan（增量扫描位置；该状态是否属于版本控制文件需明确）；
- trust / privacy rules；
- inclusion / exclusion filters；
- owner-approved notes 与来源适用范围。

密钥、个人 Token、会话内容、私有工作目录和用户绝对路径不得进入注册表或仓库。私有项目需要使用现有可信授权机制；无权访问时记录 BLOCKED，不尝试绕过权限。

### 3.2 初始配置

| source_id | 仓库 | 启用 | 初始目的 |
|---|---|---|---|
| talkdnd | `ctrlshiftaltdel/TalkDND` | true | 规则 / 存档兼容、跨模块状态、并发锁、失败恢复、命令兼容、回归测试和发行 |
| agentmgr | `ctrlshiftaltdel/AgentMgr` | true | 领域边界、治理契约、PDP/PEP、Runtime Adapter、幂等 / 租约 / 授权撤销、安全负向测试和证据边界 |

来源列表是数据配置，不是程序分支。新增来源应只要求添加配置、授权访问、通过兼容性探测；停用来源后不得再扫描。来源删除不删除已经形成的通用教训和 AgentOrch 的历史决策记录，但要移除后续扫描入口或按项目所有者指定进行归档。

### 3.3 允许学习与禁止复制的内容

允许提炼：一般化根因、架构模式、测试缺口、可复现的失败类别、审查发现、可量化的回归风险、通用设计原则、与证据挂钩的验收方法。

默认禁止复制到 AgentOrch：来源项目的业务数据、真实存档、个人信息、凭据、完整日志 / 提示词、受版权保护的规则文本，以及与改进无关的源码块。需要复现时生成合成 fixture；如果必须引用来源代码才能理解问题，应保留受控的内部证据链接，最终提交仅包含独立编写的通用规则、测试或实现。

## 4. 经验提炼、验证与去重机制

每项候选教训必须是结构化记录，并能追溯原始证据：

- lesson_id、标题、分类、来源项目与证据 URL；
- 观察事实、复现步骤 / 最小条件、根因与影响；
- 状态：OBSERVED、NEEDS_VERIFICATION、VERIFIED、REJECTED、GENERALIZED、IMPLEMENTED、REGRESSION_WATCH；
- 为什么原有流程 / 测试未能发现它；
- 可泛化规则，以及不适用场景；
- 关联模块、契约、测试、Issue / PR；
- 相似教训指纹、重复 / 冲突关系、信心等级；
- 推荐变化、成本、风险、验证命令与证据；
- 决策人、决策时间、最终结论。

### 验证原则

1. Issue 标题、审查猜测或 Agent 的自述本身不等于已证实缺陷。
2. 先读原始代码 / diff / 测试 / CI 证据；对可运行项目，在获准的隔离工作区复现。无法复现时标记为待验证或仅保留源码级风险，不得写成运行时事实。
3. 只吸收能对 AgentOrch 的通用目标产生明确收益的经验。只适用于业务模型或产品设置的教训应保留为来源专属，不强行变成核心规则。
4. 相似教训按标准化描述、来源、受影响模块、根因和相关测试进行去重；已有机制已覆盖的只记录证据或建议补齐测试，不再新增另一个规则副本。
5. 发生冲突的教训不由模型擅自选一方：记录不同证据与适用条件，要求架构决策或人工决定。
6. 每一条被采纳的教训都必须映射到至少一个明确的改进对象（契约、代码、测试、文档、流程、指标）；没有可执行后续动作的只入报告，不自动新建开发任务。

## 5. 项目架构治理与低耦合 / 高内聚检查

### 5.1 Architecture Contract

在现有项目配置与 Design Contract 基础上添加可选、可版本化的架构契约，不把一种固定目录结构强加给所有下游项目。契约至少定义：

- 模块 / 层名称、职责和状态所有权；
- 可供其他模块使用的公共接口；
- 允许依赖与禁止依赖方向；
- 特殊边界（领域 / 应用 / 适配器 / 基础设施、安全边界、生成代码等）；
- 跨模块不变量和事件 / 错误语义；
- 检查器、规则严重级别与豁免期限；
- 基线版本、契约变更决策与迁移说明。

项目没有此契约时，不应默认失败或自动生成不可信的硬门禁；可先提供只读分析报告和契约草案，待所有者冻结之后再启用阻断规则。

### 5.2 第一批自动检查

优先加入可配置、可插件化的检查器，并在当前 PR 的 CI 中执行：

- 模块依赖图、循环依赖与明确禁止的依赖边；
- 代码层 / 包层依赖方向与跨模块私有实现访问；
- 跨入口重复业务规则 / 旁路应用服务的静态规则（仅对能可靠识别的模式强制）；
- 模块扇入 / 扇出、过大模块、公共接口膨胀、跨模块改动扩散的警告；
- 模块边界契约测试与关键不变量测试；
- 套件自检与发行包中的检查器文件清单一致性。

第一批适配目标为 Python（AgentMgr）与 Rust（TalkDND）；应验证两种语言各自适用的工具链与可获得的证据。静态指标不能单独证明高内聚或低耦合；阈值默认以报告 / 警告开始，只有违反明确契约或稳定可复现的危险模式才作为硬阻断。

### 5.3 跨模块风险触发

以下任务必须在任务包中列出调用点与验证证据：

- 共享可变状态、并发读改写；
- 事务、锁、迁移、恢复和回滚；
- 状态机、跨模块事件顺序、幂等与重试；
- 身份 / 权限 / 授权 / 数据范围；
- 公共接口、适配器或协议替换；
- 影响多个模块或删除 / 重命名接口的重构。

验收覆盖正常路径、非法路径、部分失败、重复执行、并发交错、旧数据 / 旧客户端兼容和恢复后最终状态。根据实际相关性选择场景，不为填模板而虚构测试。

## 6. 安全更新引擎设计

### 6.1 逐文件分类

更新引擎必须使用旧发行清单、当前文件和新发行包做逐文件比较。至少输出以下分类：

- `UPSTREAM_UNCHANGED`：当前文件与旧发行基线一致，上游有新版，可安全候选更新；
- `ALREADY_CURRENT`：当前文件已与新发行内容一致；
- `LOCAL_MODIFICATION`：本地变化、上游未变；保留并报告；
- `THREE_WAY_CONFLICT`：本地与上游都变更；不自动覆盖，生成差异和建议；
- `PROJECT_OWNED`：项目配置、源码、测试、文档或扩展；保留；
- `UNKNOWN_FILE`：不在旧上游清单内；保留，除非明确证明其归属；
- `UPSTREAM_REMOVAL` / `UPSTREAM_RENAME`：上游删除 / 重命名；默认不删旧文件，提示兼容性与清理决策；
- `UNSAFE_PACKAGE` / `INVALID_BASELINE`：包 / 基线无法核验，整个更新停止。

旧发行清单缺失时不能把哈希差异当作覆盖许可；只提供只读盘点和手工迁移路线。对项目自己的 `docs/PROJECT.md`、`docs/PLAN.md`、应用源码 / 测试、项目私有文档、本地信息与未登记扩展，绝不自动覆盖。

### 6.2 事务和回退

- 更新前记录版本、head SHA、工作区状态、文件清单和可恢复备份。
- 用任务专属分支 / Worktree 隔离整合；不得直接在主分支执行大范围写入。
- 在暂存目录完成下载、解包、结构校验和分类；所有目标路径必须位于项目根内且无路径穿越。
- 先生成计划 / diff，再将无冲突变更作为一个可审查变更集应用。
- 应用过程中任一校验失败，避免留下半套更新；尽可能原子应用，若不能则用备份回滚并验证回滚结果。
- 保留更新报告，至少包含旧 / 新版本、来源 release、清单摘要、分类计数、冲突文件、执行命令 / 退出码、前后 SHA 与回退方式。
- 运行版本升级说明中的迁移。未经实测的命令不得写为已通过。
- 应用代码的更新与发布、合并分开；更新成功不等于已审核、已合并或已完成项目迁移。

## 7. 规则分层与包内实现原则

- 核心协作、权限、状态机、证据和合并门仍以 `AGENTS.md` / `kit/orchestration.md` 为唯一权威。
- 项目专有的经验来源、架构契约、验证命令与豁免配置放在项目配置层，不将 TalkDND / AgentMgr 的业务假设硬编码到核心。
- 会话触发语、Master 路由和可复用操作指令必须存在于正式发行包所包含的入口 / edition 文件，而不能只放在 `docs/`（`docs/` 不随发行包发布）。
- 新增的发行功能必须接入 `validate_kit.py` 的必需文件 / 结构校验、发布清单生成、包内自检与 CI；发行包不得包含真实项目源数据、凭据或学习过程中的私有材料。
- 纯标准库、可离线启动与既有 `local` / `github` 两种 edition 的核心验收语义继续保持；需要网络的“获取最新版”和跨仓库学习必须清楚标记为联网操作、失败关闭并有离线降级流程。
- 下游安装后的更新过程不等于上游代码自动发布；自我完善过程不允许更新引擎自我修改后绕过自身原有验证门。

## 8. 里程碑、交付与依赖

| 阶段 | 目标 | 主要交付 | 依赖 / 出口 |
|---|---|---|---|
| S0 契约冻结 | 一次定义经验来源、教训状态、架构契约与更新安全边界 | Schema、生命周期、来源信任模型、逐文件分类、决策 / 威胁记录 | 所有实现开始前完成；开放的安全 / 破坏性决策显式登记 |
| S1 架构契约与检查器 | 可以描述并自动检查项目架构边界 | 可选 Architecture Contract、依赖图检查器、Python / Rust 初始适配、CI 与负向测试 | S0 冻结后；违反硬规则会让 CI 失败，预警不误当成违规 |
| S2 经验来源与教训管线 | 能可靠读取、验证、去重和保存跨项目经验 | 可配置来源注册表、证据采集、候选教训记录、指纹去重、报告与隐私控制 | S0 冻结后；TalkDND / AgentMgr 初始来源均有真实证据与扫描游标 |
| S3 自我完善入口与闭环 | 一句提示词完成分析、规划、派发、实施和验证 | 入口话术、Master 路由、任务 / Issue 生成、执行与独立审查、闭环报告 | S1 + S2；合成回归能证明流程会在缺证据、来源不可达、重复教训、硬风险未决时正确停止 |
| S4 更新引擎 | 能核验最新版并安全分类整合 | 官方 Release 获取、包校验、基线识别、三方比较、冲突报告、备份 / 回滚 | S0 冻结后；正向更新、双边冲突、坏清单、路径穿越、回滚失败均有演练 |
| S5 更新入口、文档与发布 | 用户可通过自然语言更新套件 | “更新 AgentOrch”路由、GitHub / local 交付、升级指南、兼容矩阵、包内入口 | S4；发行包自检和下游合成项目更新演练通过 |
| S6 整体验收 | 验证所有流程和真实项目兼容性 | 从干净旧版本升级、冲突项目演练、经验来源回放、审计报告与残余风险 | S1–S5；当前 head 上完整 CI 通过，必要人工决策已经完成 |

## 9. 验收原则与禁止的捷径

最终验收必须证明：

1. 两句触发语及合理同义表述能路由到正确流程，不误触发普通问题。
2. 经验来源能增删停用，首次扫描和增量扫描行为可解释；未授权 / 不可访问来源不会被假装已检查。
3. 每条采纳教训都能追溯原始证据，且已验证、待验证和来源专属内容可区分。
4. 重复教训不会自动不断生成新规则或重复 Issue；没有足够收益的候选不会被强行实现。
5. 自我完善能够创建可执行的任务依赖图，并沿用现有路径锁、证据矩阵、审查 / 合并门与当前 head 验证。
6. 未经授权的安全边界、架构契约、数据迁移、锁 / 状态机或兼容性变更进入人工决策，不靠模型自行批准。
7. 架构检查对允许 / 禁止依赖都有正向与负向测试；跨语言检查器只承诺其真正验证过的能力。
8. 更新引擎能够安全下载、校验、分类、整合、回滚，且无冲突更新也不会覆盖项目配置与项目所有文件。
9. 双边修改、上游移除、无历史清单、损坏包、未提交用户修改等场景均有合成回归测试。
10. 更新报告与自我完善报告都带版本 / head SHA、证据链接、命令和退出码；未执行的检查明确标为 NOT_RUN / BLOCKED。
11. 正向控制组与负向拦截组都在 CI 中运行；禁止通过删除断言、降级测试、吞错或把失败检查移出 CI 来让任务变绿。
12. 发行包只包含为下游提供功能所需的规则、脚本、模板和静态配置，不包含开发经验源项目的私人材料、数据或密钥。

## 10. 主要风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 学到的“教训”其实是误报或尚未复现的问题 | 原始证据链接、复现或源码级证据等级、UNKNOWN / NEEDS_VERIFICATION、人工裁决 |
| 不同项目的业务约束被错误提升为核心规则 | 来源专属分类、适用范围、所有者冻结 Architecture Contract |
| 自我完善制造重复规则 / Issue / 复杂度 | 去重指纹、现有机制覆盖检查、成本 / 收益评估、提案阈值与明确非目标 |
| 提示词注入或来源内容试图修改 AgentOrch 规则 | 来源内容均视为不可信数据；只能提供证据，不得覆盖 AgentOrch 的权威规则 |
| 下载到伪造 / 损坏 / 恶意发行包 | 官方来源 allowlist、SHA / MANIFEST 校验、安全解包、失败关闭 |
| 以“更新”为由覆盖项目代码或自有配置 | 旧基线 + 当前内容 + 新版本三方分类、项目自有路径 denylist、冲突显式报告 |
| 升级中断留下半更新状态 | 暂存、备份、原子应用或回滚演练、更新报告与恢复校验 |
| 静态指标引发过多误报 | 硬门禁仅覆盖明确违约；软指标先警告并结合上下文审查 |
| 自我修改其自身检查器后绕过质量门 | 检查器和契约修改必须由原有测试 / 合成场景验证；受保护路径授权与独立审查继续生效 |

## 11. 变更与回退

- 规划文件与契约均通过专属分支和 PR 变更；功能实现按上述阶段拆为互不争用路径的任务。
- 任何对核心任务状态、锁语义、权限 / 合并门或既有 edition 行为的改变都先冻结设计契约，再实现与演练。
- 新的自我完善与更新机制可通过关闭对应入口 / feature setting 停用，不应破坏传统手工开发工作流。
- 若更新机制失败，保留旧套件版本和项目工作区；如果回滚不能被验证，应阻断后续更新并请求人工处理。
- 项目所有者可以新增 / 移除学习来源，但来源注册表的变更仍需通过可审查的配置变更。不得从一次自我完善的聊天中直接永久登记新的数据源。
